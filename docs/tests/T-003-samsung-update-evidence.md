This method collects evidence for **TV firmware (Software Update)**. Separate app/game auto-update remains an unassessed notification/overlay/restart exposure in the timing assessment; no app/game menu observation or setting change is added.

There is no assumed standby-only schedule, grace period, queue-clear effect of Off, or implication that the newest published firmware cannot update again. The manual's update warning is a hazard record, never an instruction here to start, complete or interrupt an update.

## Future collection boundary

Only after this tracked method has independent cross-vendor review and owner merge may its bounded owner observations be proposed. They use the [owner-check rule](README.md#owner-checks); no agent controls the TV. This document-only task carries out none. Any collection request must keep discovery, registry preparation and setting changes separate.

Start only with the existing ordinary Samsung PC desktop through the unchanged Denon path and TV HDMI 4, as required by the preflight. Do not power on, change input, connect anything or arrange a new display to make a check possible. Keep observations in a fresh ignored `local/T-003/` record; retain prior records unchanged. Record owner, date/time, reviewed commit and source locators. Leave unknown fields unknown; do not copy defaults or historical answers into current observations.

1. **Record owner knowledge first.** Ask for the currently known firmware/e-Manual identity and the basis/date of that knowledge; any known recent update, download, accepted/postponed update or restart prompt, Smart Hub terms acceptance, settings reset or unexplained restart; and whether TV Internet connectivity or update-bearing USB media is known present, absent or unknown. These are reports, not an inventory. Do not inspect router/device lists, networking menus, USB contents or connections, scan the network, reconnect networking or remove media. An offline report does not rule out an already downloaded package.
2. **Observe only an unambiguous passive menu.** Use ordinary Settings → Support navigation under the preflight's [Samsung navigation safeguards](T-003-discovery-preflight.md#tv-and-denon-checks). Read already visible software-version and Software Update summary text. The manual documents two possible version views: **Software Update** and **Contact Samsung**. Enter either only when applicable documentation or already available evidence establishes passive entry on this firmware; assess each route separately. Contact Samsung is described as an information screen, which is not a firmware-specific guarantee of passive entry. Record the version from whichever view meets that condition and the exact route/basis, or why neither was entered. Contact Samsung supplies no evidence about the Auto update value or a pending update. **With the currently consulted sources alone, stop before entering either view; unexposed fields remain unknown.** Do not try a view to discover its effect, use an e-Manual Try Now shortcut or borrow another model's instructions. **Do not select Remote Management, Request Support or Self Diagnosis (including Start Picture Test)**; no service request, remote access, diagnostic, test picture or QR-code action is part of this check.
3. **Transcribe existing indications.** If a passive view is safely available, record only what that view actually shows: the full firmware string, and any Auto update summary value or update/restart/progress/schedule text already displayed, with its exact wording and observation time. Read Auto update from a summary; never select its toggle to expose a value. Do not select Update now, Check, Download, Install, Restart, Schedule, Later, Accept or any equivalent action, connect USB, accept terms or change a setting. An absent indication is recorded as **no indication seen in this view**, never **no update pending**. Missing/greyed/ambiguous fields remain unknown.
4. **Stop on a prompt or deviation.** If an update, restart, agreement, connection request or progress display appears, record it and stop collection. Do not accept, dismiss, postpone, cancel, power-cycle or improvise restoration. A running update or power loss requires separate assessment; this procedure supplies no recovery action. If no such condition exists, close ordinary menus using short Return presses, observing each step; confirm the same desktop/inputs and unchanged values. Do not hold Return or repeat it blindly.

If a needed field requires a setting change, active update check, connection change or uncertain button press, collection ends at that gap. No waiting experiment, idle trial, update trial, service menu, Ex-Link or remote-control command is added. Captures are optional private evidence only if already available without adding an equipment operation; do not publish account, network or serial details.

## Assessment and closure requirements

The assessor maps each conclusion to the exact source or dated observation. An owner report can establish what was reported; it cannot fill undocumented queue or timing semantics. Record contradictions explicitly. Source/firmware mismatch, unknown or contradictory evidence means **NOT READY**.

| Applicability | Current firmware identity from an established passive version view (Software Update or Contact Samsung), or an already available report with its stated basis/date, plus source applicability. | Existing automatic-update state | A current, unchanged Auto update value with safe observation basis. On/unknown prevents clearance under this proposal. Off is only one necessary observation and never clears the gate alone. |
| Pending/downloaded/in-progress update or restart | Applicable primary documentation must explain how the available evidence excludes a staged/pending/in-progress update or deferred restart, including packages obtained before Off/offline state. ## Freshness and an outstanding attempt

Before any later authorisation decision, assess the completed private evidence and all open gaps. Immediately before a later authorised launch, repeat only the reviewed passive observations needed to confirm the argument still holds, record their time and close menus. Where these pre-launch rechecks form part of an authorised discovery session, list their exact reviewed passive steps explicitly in the session scope recorded with the dated authority in [parent section 8](T-003-meter.md#8-owners-authorisation); a bare “discovery” scope must not be read as including unspecified menu actions. This is session documentation, not a new authorisation requirement: owner-run look-only checks retain the [owner-check exemption](README.md#owner-checks) from a separate plan or physical-test authorisation, including on launch day. It grants no additional action and never permits agent-operated menus, setting changes or active checks. If the required fresh evidence cannot be obtained safely or is uncertain, do not launch. Opening menus is never added to an outstanding discovery attempt.

Any intervening update/terms acceptance, firmware or relevant setting change, network/media/input/connection change, reset, new update prompt or unexplained restart invalidates the affected argument. Mark it stale and reassess; a restarted desktop is not a revalidated record. No automatic expiry interval is invented. A later favourable state does not retrospectively authorise an earlier change.

If discovery is outstanding after 60 seconds, follow the package's [completion and waiting rules](T-003-discovery-execution.md#completion-stopping-and-outstanding-process-procedure). Do not send wake/unlock input, open update menus, prevent a restart, force-stop, power-cycle, replug or retry. Visibility loss/restart makes completion interrupted or unconfirmed, never successful merely because a picture returns. The owner retains the unconditional right to end PC activity. No safe recovery or uninterrupted-wait guarantee is introduced.
